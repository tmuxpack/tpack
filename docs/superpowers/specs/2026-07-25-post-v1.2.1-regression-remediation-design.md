# Post-v1.2.1 Regression Remediation Design

## Context

The review of `v1.2.1..731ee39` found regressions in configuration discovery,
tmux source parsing, legacy plugin migration, and the legacy update wrapper.
This design fixes findings 1 through 6 and 8 from that review. The package
metadata change that makes tmux a suggested dependency is intentional and is
out of scope.

The remediation must preserve the existing fail-closed cleanup guarantee:
tpack must not remove plugin directories when it cannot establish the complete
active plugin configuration.

## Goals

- Gather plugins from every root configuration loaded by tmux, in load order.
- Discover configurations passed through `tmux -f` automatically when a tmux
  server is available.
- Provide an explicit `@tpack-config` override for ambiguous configurations.
- Support the tmux `source-file` forms needed to build a complete source graph.
- Ignore source directives in inactive tmux conditional branches.
- Keep required active sources fail-closed and optional sources best-effort.
- Resolve and validate the plugin root before migration filesystem operations.
- Avoid requiring write access when no legacy migration is possible.
- Make legacy wrapper usage examples match repository-qualified update names.

## Non-Goals

- Reimplement the complete tmux command parser or executor.
- Change plugin identity, canonical directory naming, or migration identity
  matching.
- Restore basename-only update selection.
- Change Debian or RPM dependency metadata.
- Change the existing default configuration file chosen for TUI plugin
  insertion. A custom `tmux -f` root may become writable when no default user
  root is active.

## Configuration Root Discovery

`config.Paths` will distinguish between:

- `TmuxConf`, the single writable user configuration target used by config
  editing operations.
- `TmuxConfs`, the ordered, deduplicated root configurations used to gather
  plugin declarations.

Root discovery uses this precedence:

1. A non-empty `@tpack-config` tmux option is the authoritative root. It must
   expand to an absolute existing regular file and also becomes `TmuxConf`.
2. Otherwise, tpack asks tmux to expand `#{config_files}`. Every existing
   regular file in the returned order becomes a root. This supports servers
   started with one or more `-f` arguments.
3. If tmux cannot provide a non-empty config list, tpack checks every default
   tmux configuration candidate in upstream load order and retains every
   existing regular file.

Default discovery includes the system configuration and the user candidates
`~/.tmux.conf`, `$XDG_CONFIG_HOME/tmux/tmux.conf`, and
`~/.config/tmux/tmux.conf`, with duplicate paths removed.

The writable `TmuxConf` remains compatible with current behavior when an active
default user root exists: it is selected using the current tpack preference.
If automatic tmux discovery returns only custom roots, the last active
non-system root becomes writable because tmux processes repeated `-f` arguments
in order. System configurations are never selected as writable targets.
Failure to find any writable user or custom target remains an `ErrNoTmuxConf`
error.

The tmux runner gains a narrow format-expansion operation used for
`#{config_files}`, `source-file -F`, and conditional expressions. The real
runner uses literal `display-message -p --` arguments. The mock runner exposes
deterministic values and errors for tests.

## Source Graph Parsing

The line-level source extractor will be replaced with a focused tmux command
tokenizer for source graph construction. It will handle quoting, escaping,
comments, line continuations, command separators, and these source forms:

```text
source-file [-Fnqv] [-t target-pane] path ...
source [-Fnqv] [-t target-pane] path ...
```

Short options may be bundled. `-t` consumes its following argument or an
attached value. Every remaining path argument is processed in declaration
order.

Normal tmux path expansion supports leading home expansion and environment
variables. Tpack obtains tmux-global environment values through the runner and
falls back to the process environment when no tmux value exists. `-F` paths
are expanded through tmux format expansion before filesystem matching.

Each expanded path is passed through glob expansion. Matches are loaded in
stable lexical order. An unmatched glob or unreadable path is ignored only
when `-q` is present; otherwise it returns a contextual `SourceReadError`.
Multiple paths and nested sources retain declaration order, and canonical
clean paths are deduplicated to prevent cycles.

Malformed source commands return a contextual parse error rather than being
silently ignored. Unrelated tmux commands remain outside this parser's scope.

## Conditional Branches

Source graph construction tracks `%if`, `%elif`, `%else`, and `%endif`,
including nesting. Only directives in the active branch are processed.

Literal empty or zero conditions are false; other literal values are true.
Conditions containing tmux formats are expanded through the runner and then
interpreted using the same empty-or-zero rule. A format-expansion failure or
malformed conditional structure returns a contextual configuration error.
This preserves fail-closed behavior without treating missing files from
inactive branches as required.

When no tmux server is available, configurations without dynamic conditionals
continue to work. A dynamic conditional that cannot be evaluated fails
explicitly because tpack cannot prove the source graph complete.

## Migration Safety

`MigrateLegacy` will follow this sequence:

1. Obtain the lexical root path and return without side effects when it does
   not exist.
2. Resolve filesystem symlinks once through `Root.Resolved()` and reject unsafe
   resolved roots before creating a lock or inspecting children.
3. Pre-scan configured plugins for at least one possible legacy migration
   candidate. A candidate requires no alias, an absent canonical destination,
   and an existing non-symlink legacy directory.
4. Return without creating or opening a lock when no candidate exists.
5. Acquire the lock within the resolved root.
6. Re-run all candidate and origin checks under the lock before renaming.

All lock, origin, child, and rename operations use the stable resolved root.
The existing destination recheck remains in place. This permits read-only
roots for no-op migration paths while preserving serialized migration when a
rename may occur.

## Legacy Wrapper

`bin/update_plugins` will show repository-qualified examples such as
`tmux-plugins/tmux-sensible`. Runtime matching remains exact and no basename
compatibility layer is added.

## Error Handling

- Invalid explicit config paths identify `@tpack-config` and the rejected
  value.
- Tmux config-list discovery errors fall back to default discovery; an explicit
  override error does not fall back.
- Required active source failures include the parent file, original directive,
  and expanded target.
- Source parse and conditional errors include the configuration path and line.
- Migration errors report the resolved root and affected plugin while avoiding
  filesystem changes outside that root.
- No configuration or migration error is downgraded for `clean`.

## Testing

Configuration tests will cover:

- multiple active roots and tmux load order;
- the custom-XDG combination of `~/.tmux.conf` and
  `~/.config/tmux/tmux.conf`;
- automatic `#{config_files}` discovery and explicit override precedence;
- duplicate, missing, relative, and system-only config paths;
- preservation of the current writable target selection.

Source graph tests will cover:

- all supported flags, bundled flags, and `-t` forms;
- multiple paths, nested sources, cycles, and deterministic glob order;
- home, tmux environment, process environment, and `-F` expansion;
- optional missing paths and required missing paths;
- active, inactive, nested, malformed, and failed-format conditionals;
- quoted paths, comments, command separators, and line continuations.

Migration tests will cover:

- a root symlink that resolves to a forbidden filesystem root;
- a normal symlinked root whose stable target receives the migration;
- a read-only root with no candidate and no lock creation;
- candidate disappearance or destination creation between pre-scan and lock;
- existing lock contention and origin verification behavior.

The legacy wrapper will have a focused assertion that usage output contains
repository-qualified examples and no basename-only example.

Verification will run `make lint`, `make test`, the relevant integration test
target, and focused E2E tests for config discovery, source loading, migration,
and update wrapper behavior.
